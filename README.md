# kunpeng-tls

A small TLS 1.2 server split between a Linux Client Application (CA) and an iTrustee Trusted Application (TA). The CA accepts a TCP connection and passes encrypted records to the TA through the iTrustee client API. The TA owns the TLS identity, handshake and record processing, using the bundled Mbed TLS engine. The current server responds with the fixed body `Hello from the TEE!`.

## Status and limits

The native Linux build and TLS integration test are verified. The AArch64 cross-link, Huawei signing, installation on iTrustee and live Kunpeng runtime are not verified here. Treat the build and deployment steps below as instructions to validate in your target environment, not as a claim that the full device flow has been exercised.

This is a minimal demonstration, not a production service. It has no mutual TLS, persistent identity, remote attestation or certificate provisioning. Its self-signed server certificate is generated by the TA and is not evidence of device identity or attestation. The server handles one connection at a time. Its receive and send timeouts apply to individual socket operations, not to the full TLS handshake. The application caps HTTP headers at 4096 bytes; ciphertext queues and command input/output buffers are bounded at 64 KiB. The only enabled suite is `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`, using a P-256 identity. TLS 1.3 is not enabled. The TA manifest enables one instance, one session and keep-alive. Its ephemeral identity lasts only for that TA instance. After TA unload or device restart, export the new certificate again.

## Prerequisites

- Git with recursive submodule support, CMake 3.20 or newer, and a C compiler.
- For native tests on Linux: OpenSSL development files and the OpenSSL CLI.
- For the iTrustee build: the Huawei iTrustee SDK as the `third_party/itrustee_sdk` submodule, an AArch64 Linux cross-compiler, and the SDK inputs checked by CMake, including the TA linker script, TA headers and SDK musl headers. The upstream SDK's general sample-build instructions also list `libboundscheck`; this project's sources do not currently call it, and CMake does not check or fetch it. If your SDK variant needs it, provision the matching dependency according to that SDK's instructions.
- For the CA at runtime: the target iTrustee environment and its `/usr/lib64/libteec.so` runtime library. The project compiles the SDK CA adaptor, but does not package or provide the target runtime library or the iTrustee service infrastructure.
- For signing: Python 3, the SDK signer dependencies `pycryptodome` and `gmssl`, and the OpenSSL CLI used by the signer. You also need your own signing private key and Huawei-signed configuration/trust chain. The SDK's `config_cloud.ini` is a reference only. Do not copy its example key material or invent credentials.

No package manager or installation command is assumed here because the correct source and version depend on your build and iTrustee environments.

## Get the source

Replace `<repository-url>` below with this project's Git URL. Clone with submodules so Mbed TLS and the iTrustee SDK are present:

```sh
git clone --recurse-submodules <repository-url>
cd kunpeng-tls
```

For an existing checkout:

```sh
git submodule update --init --recursive
```

The iTrustee SDK documents Kunpeng ARM servers as a supported target and describes copying a signed `.sec` TA to `/var/itrustee/ta` and the CA to `/vendor/bin`. This project additionally fixes the CA caller path in the TA; the deployment path must match exactly.

## Native Linux build and test

Build out of source. The default build is for native development and runs the TLS integration test. It does not build the iTrustee TA.

```sh
cmake -S . -B build/native -DCMAKE_BUILD_TYPE=Release
cmake --build build/native --parallel
ctest --test-dir build/native --output-on-failure
```

The host executable is `build/native/kunpeng-tls-host`. Running it requires a working iTrustee target environment and `/usr/lib64/libteec.so`; a native compile alone does not provide these.

## AArch64 iTrustee build from x86

The TA build intentionally requires the cross-compilation mode, including when the build runs on an AArch64 machine. Do not configure a native CMake build and expect it to produce a deployable TA.

On an x86 Linux build machine with the AArch64 GNU cross compiler available as `aarch64-linux-gnu-gcc`:

```sh
cmake -S . -B build/aarch64 \
  -DCMAKE_TOOLCHAIN_FILE=cmake/aarch64-itrustee.cmake \
  -DKUNPENG_BUILD_ITRUSTEE=ON \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build/aarch64 --parallel
```

The toolchain defaults to `aarch64-linux-gnu-gcc`. To select another compiler, pass `-DITRUSTEE_C_COMPILER=` with either an absolute compiler path or an executable name on `PATH`. `-DITRUSTEE_LINUX_SYSROOT=` optionally sets the Linux CA sysroot; it is not the SDK's musl sysroot used to compile the TA.

On an AArch64 build machine that has a compiler matching the target, use the same toolchain and build mode. For example, if `gcc` is that compiler:

```sh
cmake -S . -B build/aarch64 \
  -DCMAKE_TOOLCHAIN_FILE=cmake/aarch64-itrustee.cmake \
  -DITRUSTEE_C_COMPILER=gcc \
  -DKUNPENG_BUILD_ITRUSTEE=ON \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build/aarch64 --parallel
```

CMake's `CMAKE_SYSTEM_NAME=Linux` still makes this an explicit cross build. This mode is required by the project even on Kunpeng.

Expected outputs:

- `build/aarch64/kunpeng-tls-host`: AArch64 Linux CA executable.
- `build/aarch64/ta/unsigned/libcombine.so` and `build/aarch64/ta/unsigned/manifest.txt`: unsigned TA build inputs. `libcombine.so` is **not deployable**. Do not copy it to the device as a TA.

The configured TA UUID is `1f8c4d90-7b36-4e21-a509-6d2c83f047b1`.

## Sign the TA

Signing is opt-in. Provide your own absolute path to the private signing configuration supplied for your target and signing authority. The file must refer to an authorized private key and Huawei-signed configuration/trust chain suitable for the target. The SDK's `third_party/itrustee_sdk/build/signtools/config_cloud.ini` documents configuration fields, but is only an example and is not a credential. The repository does not include a usable private key or trusted signing configuration and the build does not generate them.

Configure and build with signing enabled:

```sh
cmake -S . -B build/aarch64 \
  -DCMAKE_TOOLCHAIN_FILE=cmake/aarch64-itrustee.cmake \
  -DKUNPENG_BUILD_ITRUSTEE=ON \
  -DKUNPENG_SIGN_TA=ON \
  -DITRUSTEE_SIGN_PRIVATE_CONFIG=/absolute/path/to/your/authorized-signing-config.ini \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build/aarch64 --parallel
```

Replace `/absolute/path/to/your/authorized-signing-config.ini` with the absolute path to your real config. The signer uses the SDK's `signtool_v3.py` and the `--privateCfg` argument. It names the signed artifact from the TA manifest; with this project's UUID the expected name is `build/aarch64/ta/signed/1f8c4d90-7b36-4e21-a509-6d2c83f047b1.sec`. Confirm the file emitted by the signer rather than assuming signing succeeded. Only the signed `.sec` artifact is intended for deployment. Validate that signature, permissions, TA UUID and required loader imports are accepted by the target's iTrustee policy and trust chain. A successful CMake target alone does not establish that the target will load it.

## Deploy to iTrustee

Use the target's approved deployment process to copy the AArch64 host executable to exactly `/vendor/bin/kunpeng-tls-host`, owned/executable as required by the system. The TA hard-codes this path and the caller identity `root` in its iTrustee caller allowlist. If the CA is installed under a different path, TA creation will fail unless the code and policy are deliberately changed together.

Install the signed TA at:

```text
/var/itrustee/ta/1f8c4d90-7b36-4e21-a509-6d2c83f047b1.sec
```

If your platform permits direct file installation, run the following on the Kunpeng server from the repository root (transfer the `build/aarch64` artifacts there first if you built elsewhere):

```sh
sudo install -d /vendor/bin /var/itrustee/ta
sudo install -o root -g root -m 0755 \
  build/aarch64/kunpeng-tls-host /vendor/bin/kunpeng-tls-host
sudo install -o root -g root -m 0644 \
  build/aarch64/ta/signed/1f8c4d90-7b36-4e21-a509-6d2c83f047b1.sec \
  /var/itrustee/ta/1f8c4d90-7b36-4e21-a509-6d2c83f047b1.sec
```

Otherwise, use your platform's supported mechanism to install the TA and required signing configuration. Never copy the signing private key to the target as part of deployment. Confirm that the target loader accepts the signature, permission policy, UUID and imports before running the CA. The SDK's general README refers to copying artifacts to the above directories; it does not replace your system's security controls. This README does not prescribe OP-TEE services or supplicants.

The CA uses the iTrustee SDK adaptor and requires the literal runtime library path `/usr/lib64/libteec.so` on the target. Ensure that library and the target's iTrustee runtime are available. The SDK/adaptor setup here does not package them.

## Start and validate

Run the CA as root at its allowlisted path. Replace the `.sec` path only if your signer emitted the expected UUID-named artifact elsewhere:

```sh
sudo /vendor/bin/kunpeng-tls-host \
  --certificate-out /var/tmp/kunpeng-tls-server.pem \
  --port 8443 \
  --ta /var/itrustee/ta/1f8c4d90-7b36-4e21-a509-6d2c83f047b1.sec
```

The default bind address is `127.0.0.1`, so this accepts local connections only. In another shell on the target, validate TLS and the fixed response using the exported certificate:

```sh
curl --cacert /var/tmp/kunpeng-tls-server.pem https://localhost:8443/
```

The expected response is:

```text
Hello from the TEE!
```

Do not use `curl -k`. The certificate is self-signed and the host exports it from the TA. It is not attestation. Before trusting it, obtain and verify its fingerprint through an independent trusted channel. `--cacert` makes this test trust the exported certificate; it does not establish that the certificate belongs to a known or attested device.

To accept remote IPv4 connections, bind to the server's chosen interface address by passing `--bind SERVER_IP` (replace `SERVER_IP` with the actual IPv4 address). Then, from a client that has independently obtained and validated the server certificate, preserve the `localhost` hostname for certificate verification while connecting to that address:

```sh
curl --resolve localhost:8443:SERVER_IP \
  --cacert /path/to/independently-verified-server.pem \
  https://localhost:8443/
```

Replace `SERVER_IP` and `/path/to/independently-verified-server.pem` with the real server IPv4 address and verified certificate path. Do not treat a certificate fetched over the same untrusted connection as independent verification. Stop the server with Ctrl-C.

The server accepts connections sequentially, one at a time. Its 15-second socket receive/send timeout is per socket operation. It does not impose a total handshake deadline.

## Troubleshooting

- **Cross compiler not found:** set `ITRUSTEE_C_COMPILER` to the cross-compiler executable name on `PATH` or its absolute path. On Kunpeng, explicitly select the target-matching compiler and still use the toolchain file.
- **SDK input missing:** initialize submodules recursively and check that the SDK contains the TA headers, linker script and musl files checked by CMake. Any additional dependency required by a different SDK variant must be supplied separately.
- **CA cannot initialize or open a session:** verify `/usr/lib64/libteec.so`, the iTrustee runtime and TA installation. Check the printed TEEC result and origin.
- **TA creation denied:** check the `.sec` UUID, signature and trust chain, loader imports, permissions, and that the CA runs as `root` from exactly `/vendor/bin/kunpeng-tls-host`.
- **Signing fails:** confirm the private config path is absolute and exists, its key and Huawei-signed config/trust chain are authorized for the target, and the signer dependencies and OpenSSL CLI are available. Do not substitute the SDK's reference `config_cloud.ini` for real signing credentials.
- **curl hostname or certificate error:** use `https://localhost:8443/` with the exported certificate for local validation. For remote IPv4, use `--resolve` so TLS still validates `localhost`; do not disable certificate checks. Export a fresh certificate if the TA instance has been recreated.
