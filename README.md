# kunpeng-tls

A small TLS 1.2/1.3 server split between a Linux Client Application (CA) and an iTrustee Trusted Application (TA). The CA accepts a TCP connection and passes encrypted records to the TA through the iTrustee client API. The TA owns the TLS identity, handshake and record processing, using OpenSSL 3.5. Bodyless GET requests receive the fixed response `Hello from the TEE!`; a bodyless POST to `/` demonstrates a bounded host-data exchange over TLS.

## Status and limits

The native Linux build and TLS integration test are verified. AArch64 compilation and linking of the CA and unsigned TA are also verified with Arm GNU Toolchain 14.3.Rel1 on x86-64 Linux. Huawei signing, installation on iTrustee and live Kunpeng runtime are not verified here. Treat the build and deployment steps below as instructions to validate in your target environment, not as a claim that the full device flow has been exercised.

This is a minimal demonstration, not a production service. It has no mutual TLS, persistent identity, remote attestation or certificate provisioning. Its self-signed server certificate is generated by the TA and is not evidence of device identity or attestation. The C++17 CA multiplexes concurrent IPv4 clients with a fixed worker pool; TLS remains entirely inside the TA. The trusted side serializes access to its shared identity and TLS state, so concurrent clients do not imply parallel trusted execution or a throughput guarantee. At most eight client sessions are admitted. The application caps HTTP headers at 4096 bytes; ciphertext queues and command input/output buffers are bounded at 64 KiB. TLS is bounded to versions 1.2 through 1.3. TLS 1.2 retains only `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`. TLS 1.3 enables `TLS_AES_256_GCM_SHA384`, `TLS_AES_128_GCM_SHA256` and `TLS_CHACHA20_POLY1305_SHA256`. The key-exchange policy prefers the hybrid tuple `X25519MLKEM768:SecP256r1MLKEM768:SecP384r1MLKEM1024` ahead of the classical tuple `X25519:X448:P-256:P-384:P-521:ffdhe3072:ffdhe4096:ffdhe6144:ffdhe8192`, with server preference within each tuple. FFDHE is usable here with TLS 1.3; the retained TLS 1.2 suite uses ECDHE. `ffdhe2048` and obsolete groups are excluded. Authentication still uses a P-256 ECDSA identity (about 128-bit classical security); hybrid key exchange does not make authentication post-quantum or raise the whole connection to 256-bit security. Session caching and TLS 1.3 session-ticket issuance are disabled. The TA manifest enables one instance, multiple sessions and keep-alive; TA code enforces the eight-session cap. Its ephemeral identity lasts only for that TA instance. After TA unload or device restart, export the new certificate again.

## Prerequisites

- Git with recursive submodule support, CMake 3.20 or newer, a C compiler and a C++17 compiler.
- For native tests on Linux: OpenSSL 3.5 or newer development files and the OpenSSL CLI.
- For the TA: Perl and GNU make. During iTrustee configuration, CMake FetchContent downloads pristine OpenSSL 3.5.9 sources from openssl.org and verifies SHA-256 `603f5602e2eef00d77fbd429d34dcd5822bb301757a1bc9cdb24c670f1eb859a`. The sources include the Apache License 2.0 text at `LICENSE.txt`; an initial TA configuration therefore requires network access. No external SGX checkout or prebuilt x86 library archive is needed.
- For the iTrustee build: the Huawei iTrustee SDK as the `third_party/itrustee_sdk` submodule, an AArch64 Linux cross-compiler, and the SDK inputs checked by CMake, including the TA linker script, TA headers and SDK musl headers. The upstream SDK's general sample-build instructions also list `libboundscheck`; this project's sources do not currently call it, and CMake does not check or fetch it. If your SDK variant needs it, provision the matching dependency according to that SDK's instructions.
- For the CA at runtime: the target iTrustee environment and its `/usr/lib64/libteec.so` runtime library. The project compiles the SDK CA adaptor, but does not package or provide the target runtime library or the iTrustee service infrastructure.
- For signing: Python 3, the SDK signer dependencies `pycryptodome` and `gmssl`, and the OpenSSL CLI used by the signer. You also need your own signing private key and Huawei-signed configuration/trust chain. The SDK's `config_cloud.ini` is a reference only. Do not copy its example key material or invent credentials.

No package manager or installation command is assumed here because the correct source and version depend on your build and iTrustee environments.

## Get the source

Replace `<repository-url>` below with this project's Git URL. Clone with submodules so the iTrustee SDK is present. OpenSSL TA sources are fetched and checksum-verified when configuring the iTrustee build; network access is required. The SDK, toolchain and other prerequisites above are still required:

```sh
git clone --recurse-submodules <repository-url>
cd kunpeng-tls
```

For an existing checkout:

```sh
git submodule update --init --recursive
```

The iTrustee SDK documents Kunpeng ARM servers as a supported target and describes copying a signed `.sec` TA to `/var/itrustee/ta` and the CA to `/vendor/bin`. This project additionally fixes the CA caller path in the TA; the deployment path must match exactly.

## Native Linux build and test

Build out of source. The default build is for native development and runs the TLS integration test. It uses installed system OpenSSL 3.5 or newer and does not download TA sources or build the iTrustee TA.

```sh
cmake -S . -B build/native -DCMAKE_BUILD_TYPE=Release
cmake --build build/native --parallel
ctest --test-dir build/native --output-on-failure
```

The host executable is `build/native/kunpeng-tls-host`. Running it requires a working iTrustee target environment and `/usr/lib64/libteec.so`; a native compile alone does not provide these.

## AArch64 iTrustee build from x86

The TA build intentionally requires the cross-compilation mode, including when the build runs on an AArch64 machine. Do not configure a native CMake build and expect it to produce a deployable TA.

On an x86 Linux build machine with the AArch64 GNU cross compiler available as `aarch64-linux-gnu-gcc`:

```sh
cmake -S . -B build/aarch64 \
  -DCMAKE_TOOLCHAIN_FILE=cmake/aarch64-itrustee.cmake \
  -DKUNPENG_BUILD_ITRUSTEE=ON \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build/aarch64 --parallel
```

The toolchain defaults to `aarch64-linux-gnu-gcc` and infers the adjacent matching `g++`. To select another C compiler, pass `-DITRUSTEE_C_COMPILER=` with either an absolute compiler path or an executable name on `PATH`. For example, the local Arm toolchain uses `-DITRUSTEE_C_COMPILER=/home/afrizal/Documents/Development/arm-gnu-toolchain-14.3.rel1-x86_64-aarch64-none-linux-gnu/bin/aarch64-none-linux-gnu-gcc`. Override the matching C++ compiler with `-DITRUSTEE_CXX_COMPILER=/absolute/path/to/aarch64-g++` when needed; never use the x86 host C++ compiler. Only the Linux CA uses C++ and its runtime; the TA and SDK adaptor remain C. `-DITRUSTEE_LINUX_SYSROOT=` optionally sets the Linux CA sysroot; it is not the SDK's musl sysroot used to compile the TA.

On an AArch64 build machine that has a compiler matching the target, use the same toolchain and build mode. For example, if `gcc` is that compiler:

```sh
cmake -S . -B build/aarch64 \
  -DCMAKE_TOOLCHAIN_FILE=cmake/aarch64-itrustee.cmake \
  -DITRUSTEE_C_COMPILER=gcc \
  -DKUNPENG_BUILD_ITRUSTEE=ON \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build/aarch64 --parallel
```

CMake's `CMAKE_SYSTEM_NAME=Linux` still makes this an explicit cross build. This mode is required by the project even on Kunpeng.

Expected outputs:

- `build/aarch64/kunpeng-tls-host`: AArch64 Linux CA executable.
- `build/aarch64/ta/unsigned/libcombine.so` and `build/aarch64/ta/unsigned/manifest.txt`: unsigned TA build inputs. `libcombine.so` is **not deployable**. Do not copy it to the device as a TA.

The TA builds static OpenSSL libssl/libcrypto from pristine sources in the build directory, with `no-sock no-posix-io no-stdio no-dso no-shared no-threads no-module` and `--with-rand-seed=none`. It keeps SDK-only `-nostdinc` compilation and `-nostdlib` linking. Build-local compatibility patches disable directory enumeration and inherited process environment, use OpenSSL's portable aligned allocator, and remove unused Linux entropy-header dependencies. No host TLS library is linked into the TA or CA.

The platform adapter maps clocks to SDK `get_sys_rtc_time`/`TEE_GetSystemTime` and waits to `TEE_Wait`; filesystem queries fail explicitly with ENOSYS. RTC accuracy and trust require device validation. The engine must register its per-identity builtin entropy provider before generating keys or TLS randomness; this build deliberately provides no OS entropy fallback. The post-link check rejects imports absent from SDK headers, apart from SDK sample stack-protector hooks; compiler arithmetic helpers are linked from the matching AArch64 libgcc. Header declarations are not proof of the target loader's exports: signing, loader acceptance, entropy behavior, and the manifest's 2 MiB heap/64 KiB stack budget remain unverified on device.

The configured TA UUID is `1f8c4d90-7b36-4e21-a509-6d2c83f047b1`.

## Sign the TA

Signing is opt-in. Provide your own absolute path to the private signing configuration supplied for your target and signing authority. The file must refer to an authorized private key and Huawei-signed configuration/trust chain suitable for the target. The SDK's `third_party/itrustee_sdk/build/signtools/config_cloud.ini` documents configuration fields, but is only an example and is not a credential. The repository does not include a usable private key or trusted signing configuration and the build does not generate them.

Configure and build with signing enabled:

```sh
cmake -S . -B build/aarch64 \
  -DCMAKE_TOOLCHAIN_FILE=cmake/aarch64-itrustee.cmake \
  -DKUNPENG_BUILD_ITRUSTEE=ON \
  -DKUNPENG_SIGN_TA=ON \
  -DITRUSTEE_SIGN_PRIVATE_CONFIG=/absolute/path/to/your/authorized-signing-config.ini \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build/aarch64 --parallel
```

Replace `/absolute/path/to/your/authorized-signing-config.ini` with the absolute path to your real config. The signer uses the SDK's `signtool_v3.py` and the `--privateCfg` argument. It names the signed artifact from the TA manifest; with this project's UUID the expected name is `build/aarch64/ta/signed/1f8c4d90-7b36-4e21-a509-6d2c83f047b1.sec`. Confirm the file emitted by the signer rather than assuming signing succeeded. Only the signed `.sec` artifact is intended for deployment. Validate that signature, permissions, TA UUID and required loader imports are accepted by the target's iTrustee policy and trust chain. A successful CMake target alone does not establish that the target will load it.

Changing the TLS policy requires rebuilding the TA, signing the new unsigned output with your authorized signing configuration, and redeploying the new `.sec`. An already-installed signed TA keeps its old policy; rebuilding or replacing only the CA does not enable TLS 1.3. No signing key is supplied or generated by this change. Validate hybrid handshakes and the unchanged heap/stack budgets on the target before deployment approval.

## Deploy to iTrustee

Use the target's approved deployment process to copy the AArch64 host executable to exactly `/vendor/bin/kunpeng-tls-host`, owned/executable as required by the system. The TA hard-codes this path and the caller identity `root` in its iTrustee caller allowlist. If the CA is installed under a different path, TA creation will fail unless the code and policy are deliberately changed together.

Install the signed TA at:

```text
/var/itrustee/ta/1f8c4d90-7b36-4e21-a509-6d2c83f047b1.sec
```

If your platform permits direct file installation, run the following on the Kunpeng server from the repository root (transfer the `build/aarch64` artifacts there first if you built elsewhere):

```sh
sudo install -d /vendor/bin /var/itrustee/ta
sudo install -o root -g root -m 0755 \
  build/aarch64/kunpeng-tls-host /vendor/bin/kunpeng-tls-host
sudo install -o root -g root -m 0644 \
  build/aarch64/ta/signed/1f8c4d90-7b36-4e21-a509-6d2c83f047b1.sec \
  /var/itrustee/ta/1f8c4d90-7b36-4e21-a509-6d2c83f047b1.sec
```

Otherwise, use your platform's supported mechanism to install the TA and required signing configuration. Never copy the signing private key to the target as part of deployment. Confirm that the target loader accepts the signature, permission policy, UUID and imports before running the CA. The SDK's general README refers to copying artifacts to the above directories; it does not replace your system's security controls. This README does not prescribe OP-TEE services or supplicants.

The CA uses the iTrustee SDK adaptor and requires the literal runtime library path `/usr/lib64/libteec.so` on the target. Ensure that library and the target's iTrustee runtime are available. The SDK/adaptor setup here does not package them.

## Start and validate

Run the CA as root at its allowlisted path. Replace the `.sec` path only if your signer emitted the expected UUID-named artifact elsewhere:

```sh
sudo /vendor/bin/kunpeng-tls-host \
  --certificate-out /var/tmp/kunpeng-tls-server.pem \
  --port 8443 \
  --ta /var/itrustee/ta/1f8c4d90-7b36-4e21-a509-6d2c83f047b1.sec
```

The default bind address is `127.0.0.1`, so this accepts local connections only. In another shell on the target, validate TLS and the fixed response using the exported certificate:

```sh
curl --cacert /var/tmp/kunpeng-tls-server.pem https://localhost:8443/
```

With an OpenSSL 3.5 client, explicitly validate hybrid negotiation and certificate verification (the summary should report TLS 1.3 and `X25519MLKEM768`):

```sh
printf 'GET / HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' | \
  openssl s_client -connect localhost:8443 -servername localhost \
    -tls1_3 -groups X25519MLKEM768 -CAfile /var/tmp/kunpeng-tls-server.pem \
    -verify_hostname localhost -verify_return_error -no_ign_eof
```

The single-request OpenSSL example sends `Connection: close` to request connection termination after the response.

HTTP/1.1 connections are persistent by default for sequential requests. A `close` token in the `Connection` header requests closure after the response; header names and connection tokens are case-insensitive, including `close` within a comma-separated token list. HTTP/1.0 connections close after the response, even when keep-alive is requested. This supports sequential HTTP/1.1 requests, not HTTP/2 or HTTP pipelining.

Bodyless `GET` requests remain unchanged. `Content-Length` may be absent or occur exactly once with a valid decimal value of zero. The only supported POST is a bodyless `POST /` with exactly one `Content-Length: 0`. POST to any other path, any request body, and any `Transfer-Encoding` are unsupported; invalid or duplicate `Content-Length` headers are rejected and the connection is closed. No request body is forwarded to the CA.

The demo POST causes the TA to request the fixed public data `Public demo data from CA.\n`. The TA parses the request and issues a `HOST_REQUEST` containing operation `DEMO_DATA` and its request ID. The CA supplies the public data with `TLS_CMD_SUPPLY_HOST_DATA=3`; existing `PROCESS=1` and `CERTIFICATE=2` commands remain. Only operation/ID metadata crosses from TA to CA, not plaintext HTTP. The returned host data goes back to the TA, where it is copied and checked as 1 to 128 printable ASCII bytes or LF. CR, NUL and other control bytes are rejected, as are replayed operation/ID pairs. The TA builds the bounded HTTP response and encrypts it with TLS.

Host-supplied response data is untrusted input, not an authenticated key record. The TA does not rely on it for authorization. This is a fixed demo callback, not an arbitrary filesystem, network or request-body service. There can be only one pending request per connection, and each worker invocation performs at most one host dispatch; it does not recursively request more host work. Existing GET keep-alive and explicit-close behavior is preserved. The existing eight-session limit also remains; the POST does not increase it.

Persistent connections do not change the eight-session cap or host deadlines: eight persistent connections hold all eight TA sessions, including while idle, until they close or time out. The default handshake deadline and idle timeout remain 15 seconds each.

For the existing GET response, the expected body remains:

```text
Hello from the TEE!
```

To request the demo host-data response, use exactly this bodyless POST:

```sh
curl --cacert /var/tmp/kunpeng-tls-server.pem \
  --request POST \
  --header 'Content-Length: 0' \
  https://localhost:8443/
```

Do not use `curl -k`. The certificate is self-signed and the host exports it from the TA. It is not attestation. Before trusting it, obtain and verify its fingerprint through an independent trusted channel. `--cacert` makes this test trust the exported certificate; it does not establish that the certificate belongs to a known or attested device.

To accept remote IPv4 connections, bind to the server's chosen interface address by passing `--bind SERVER_IP` (replace `SERVER_IP` with the actual IPv4 address). Then, from a client that has independently obtained and validated the server certificate, preserve the `localhost` hostname for certificate verification while connecting to that address:

```sh
curl --resolve localhost:8443:SERVER_IP \
  --cacert /path/to/independently-verified-server.pem \
  https://localhost:8443/
```

Replace `SERVER_IP` and `/path/to/independently-verified-server.pem` with the real server IPv4 address and verified certificate path. Do not treat a certificate fetched over the same untrusted connection as independent verification. Stop the server with Ctrl-C.

The CLI preserves `--certificate-out FILE` (required), `--port PORT` (default 8443), `--bind IPv4` (default 127.0.0.1), `--ta PATH` (optional), and `--help`. `--workers N` selects 1..32 workers (default 4); `--max-connections N` selects 1..8 admitted clients (default 8), bounded by the TA session cap. Numeric options require positive decimal integers. Certificate export completes before the listener starts, and export/startup errors return nonzero.

The host bounds pending work to 16 queued jobs and 1 MiB of queued input, with a 256 KiB per-client outbound limit. Its default handshake deadline and idle timeout are each 15 seconds; these are host-level deadlines, not individual blocking socket operation timeouts. Queue saturation applies backpressure rather than allowing unbounded allocation. SIGINT (Ctrl-C) and SIGTERM request graceful shutdown through a blocked-signal waiter; the host stops and joins its workers before destroying the iTrustee backend. These concurrency and shutdown paths are exercised by native tests with test backends, not a live iTrustee device.

## k6 load test

First confirm that the running server returns the expected response. Then run:

```sh
k6 run --summary-mode full tests/load_test.js
```

The defaults are 2 virtual users for 30 seconds against `https://localhost:8443/`, using TLS 1.3. Certificate verification is skipped by default for this load test, as requested; this does not authenticate the server. `CONNECTION_REUSE` defaults to `true`, setting `noConnectionReuse: false` so k6 can reuse persistent HTTP/1.1 connections for sequential requests. Set `CONNECTION_REUSE=false` for a fresh TCP/TLS connection per request (handshake-load mode):

```sh
k6 run --summary-mode full -e CONNECTION_REUSE=false tests/load_test.js
```

```sh
k6 run --summary-mode full \
  -e URL=https://localhost:8443/ \
  -e VUS=2 -e DURATION=60s -e TLS_VERSION=tls1.3 \
  -e P95_MS=1000 -e FAILURE_RATE=0.01 \
  tests/load_test.js
```

`VUS`, `DURATION`, `URL`, `TLS_VERSION` (`tls1.2` or `tls1.3`), `P95_MS`, `FAILURE_RATE`, `INSECURE_SKIP_TLS_VERIFY`, and `CONNECTION_REUSE` are configurable environment inputs. `CONNECTION_REUSE` accepts only the exact strings `true` and `false`; its inverse sets k6's `noConnectionReuse` option. Keep VUs within the host's admitted connection limit for a normal capacity measurement; exceeding it deliberately measures overload/rejections. Requests have a 10-second timeout and do not follow redirects.

The summary reports p50, p90, p95, and p99 for request duration and TLS handshake timing. All checks must pass: HTTP 200, exact `Hello from the TEE!\n` body, and the requested TLS version. The `FAILURE_RATE` and `P95_MS` threshold expressions remain commented out; only the checks threshold is enabled. `http_req_duration` excludes connection establishment and TLS negotiation; use `http_req_tls_handshaking` and `iteration_duration` to interpret those costs. With connection reuse enabled, requests on an existing connection do not perform a new TLS handshake, so aggregate handshake timings include zero-cost reused requests and are not per-handshake latency measurements. Use `-e CONNECTION_REUSE=false` to measure fresh-handshake load and compare it separately with reused-connection request timing. Run with `--summary-mode full` to display all timing metrics on k6 versions supporting that option.

To enable certificate verification on Linux:

```sh
SSL_CERT_FILE=/var/tmp/kunpeng-tls-server.pem \
  k6 run --summary-mode full -e INSECURE_SKIP_TLS_VERIFY=false tests/load_test.js
```

The certificate must match the current TA identity and URL hostname. k6 checks the TLS version but this script does not select or assert the negotiated key-exchange group. Verify hybrid PQC separately with the OpenSSL command above before interpreting load results as hybrid-PQC performance. Local fixture smoke tests validate the script, not Kunpeng throughput.

## Integration with kripta-key

The host follows the same ownership split as kripta-key's `RestAPIHost`: the event loop owns sockets and connection buffers, workers own backend calls, and eventfd carries completion wakeups. `TlsSessionService` separates that transport from iTrustee. Its open/process/close operations map to `AbstractRestSessionService::restSessionOpen`, `restSessionProcess`, and `restSessionClose`; process output and flags map to ciphertext output, `written`, `shouldClose`, `hasMoreData`, and `handshakeComplete`.

This standalone project does not depend on kripta-key's `core::Expect`, `ErrorCode`, or `compat::span`, so it is not a drop-in implementation of that interface. Integration should adapt the iTrustee service to those existing types and reuse kripta-key's host rather than install a second event loop. The iTrustee implementation has no SGX worker-entry context or trusted socket registration requirement; those interface hooks need explicit backend-specific semantics. TLS identity, private keys, and plaintext stay in the TA. No kripta-key source files are modified here.

Host connections can progress concurrently, but SDK operations and trusted OpenSSL access are serialized per operation. A stalled socket therefore does not hold the trusted gate. An entered TEEC call cannot be cancelled by this host; shutdown must wait for it to return before closing its session or destroying the backend.

## Troubleshooting

- **Cross compiler not found:** set `ITRUSTEE_C_COMPILER` to the cross-compiler executable name on `PATH` or its absolute path. On Kunpeng, explicitly select the target-matching compiler and still use the toolchain file.
- **SDK input missing:** initialize submodules recursively and check that the SDK contains the TA headers, linker script and musl files checked by CMake. Any additional dependency required by a different SDK variant must be supplied separately.
- **CA cannot initialize or open a session:** verify `/usr/lib64/libteec.so`, the iTrustee runtime and TA installation. Check the printed TEEC result and origin.
- **TA creation denied:** check the `.sec` UUID, signature and trust chain, loader imports, permissions, and that the CA runs as `root` from exactly `/vendor/bin/kunpeng-tls-host`.
- **Signing fails:** confirm the private config path is absolute and exists, its key and Huawei-signed config/trust chain are authorized for the target, and the signer dependencies and OpenSSL CLI are available. Do not substitute the SDK's reference `config_cloud.ini` for real signing credentials.
- **curl hostname or certificate error:** use `https://localhost:8443/` with the exported certificate for local validation. For remote IPv4, use `--resolve` so TLS still validates `localhost`; do not disable certificate checks. Export a fresh certificate if the TA instance has been recreated.
